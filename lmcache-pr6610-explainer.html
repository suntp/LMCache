1. Before / after: command shape and flag placement

1. 前后对比：命令结构与参数位置

Previously KVCacheCommand was a single BaseCommand whose parser registered output flags at the parent level, so users had to write lmcache kvcache --format json list … and the docs had to explain the ordering. Now the command mirrors lmcache quota: an almost-empty CompositeCommand whose leaf modules are auto-discovered; BaseCommand.register appends the shared output arguments to every leaf, so lmcache kvcache list --format json works naturally.

此前 KVCacheCommand 是单个 BaseCommand，输出参数注册在父级 parser 上，用户必须写 lmcache kvcache --format json list …，文档还得专门解释顺序。现在与 lmcache quota 同构：近乎空的 CompositeCommand 自动发现 leaf 模块；BaseCommand.register 给每个 leaf 追加共享输出参数，于是 lmcache kvcache list --format json 自然可用。

Breaking change (intended, per review): the parent level no longer accepts --format/--output/-q. lmcache kvcache --format json clear (old) now exits 2; use lmcache kvcache clear --format json. Locked by test_output_flags_belong_to_subcommands.
破坏性变更（审查意见所要求）：父级不再接受 --format/--output/-q。旧的 lmcache kvcache --format json clear 现在退出码 2；请用 lmcache kvcache clear --format json。由 test_output_flags_belong_to_subcommands 锁定。

2. fetch_json: one error path, every code, bounded reads

2. fetch_json：统一错误路径、全状态码、有界读取

Files: lmcache/cli/http.py. The helper gained keyword-only method/data (so clear could reuse it instead of a near-duplicate), and its HTTPError branch was rebuilt around one _error_body() read with the following guarantees:

文件：lmcache/cli/http.py。helper 新增仅关键字参数 method/data（让 clear 复用它而非近似重复的私有实现），HTTPError 分支围绕单一的 _error_body() 读取重建，保证如下：

  • Bounded: at most 4096 bytes are read for diagnostics (read(cap+1), then sliced); the response is always closed (finally: exc.close()).
  • 有界：诊断最多读 4096 字节（read(cap+1) 后切片）；响应总是被关闭（finally: exc.close()）。
  • Short bodies detected: a bounded read silently returns fewer bytes when a declared Content-Length ends early; the declared length is checked and an IncompleteRead(raw, expected-len(raw)) is chained, reproducing the legacy "…94 more expected" diagnostics. HEAD requests and 204/304 statuses legitimately carry no body (RFC 9110 §8.6) and are exempt.
  • 短读检测：声明 Content-Length 提前截断时，有界 read 会静默返回短字节；代码核对声明长度并链式抛出 IncompleteRead(raw, expected-len(raw))，复现旧版 "…94 more expected" 诊断。HEAD 请求与 204/304 状态合理无正文（RFC 9110 §8.6），予以豁免。
  • Strict incremental UTF-8: the prefix is decoded with codecs' incremental decoder, final=not truncated — a multi-byte character split by the bound is tolerated, invalid bytes anywhere still raise and map to Cannot read HTTP {code} response.
  • 增量严格 UTF-8：前缀用 codecs 增量解码器、final=not truncated——被上限切开的尾字符被容忍，但任何位置的非法字节仍会抛出并映射为 Cannot read HTTP {code} response。
  • Detail extraction is truncation-safe: _error_body returns (text, truncated); the JSON detail/error/message extraction runs on the unmarked text, and [truncated] is appended only when a 503 falls back to showing the raw body.
  • 截断不影响提取：_error_body 返回 (text, truncated)；JSON 的 detail/error/message 提取作用于未加标记的文本，[truncated] 仅在 503 回退展示原始 body 且确实截断时追加。
  • 503 contract preserved: Server unhealthy: {detail|raw body} (design doc & test_describe.py expectations, incl. plain-text bodies and the __cause__.__cause__ is IncompleteRead chain) — while detail bodies now render properly instead of raw JSON.
  • 503 契约保留：Server unhealthy: {detail|raw body}（设计文档与 test_describe.py 的既有期望，含纯文本正文和 __cause__.__cause__ is IncompleteRead 异常链）——同时 detail 正文不再以原始 JSON 串形式展示。
